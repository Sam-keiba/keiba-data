Target取り込み DB設計報告書

keiba-data のローカルDBを、Targetからエクスポートした race_data（1995〜2026年、約152万行）と horse_data（約14万頭）で拡張するための調査結果・変更案と、その実装結果。

01概要

Target（TARGET frontier JV）から手動エクスポートしたCSV（datasets_from_target/）を全て keiba-data のローカルDBに取り込み、 既存のスクレイピング由来DB（2023年以降）を置き換えずに拡張するための設計と、その実装結果。01〜07 が設計（承認時点）、08 が実装結果。 承認時の決定（07）により、本体テーブルを Target に基づいて1995年〜現在まで構築し、既存行の空欄も Target で埋めた。

  • Target の race_data は1995-01-05〜2026-09-13・109,440レース。既存DBとの重複期間（2023-01-05〜2026-09-13）では 12,855レース・177,171行がIDで全件対応し、主要13項目が100%一致した。
  • キーは既存と共通：race_id（Target 18桁IDから算出）、horse_id＝血統登録番号、騎手・調教師・馬主コード。名前による突合は不要。

2.2 ER図

実線＝外部キー（schema で宣言）または親子関係、破線＝同じキー体系による論理的な結合（外部キー制約なし）。緑の破線は target_* から本体へのマージ（target_races→races、target_runs→entries/results、target_horses→horses）。 races と horses には出所の source 列 CHG を追加し、本体の空欄を埋めた記録は target_fills NEW（図では省略）。 target_runs.jockey_id / trainer_id も jockeys / trainers と同じ体系。運用・トークン系テーブル（runs, fetch_log, jra_*_links 等）は省略。

項目方針
事前バックアップ書き込み前に対象DBを data/backup/keiba_YYYYMMDD_HHMMSS.db へ SQLite の backup API で複製（WAL を含めて一貫したコピーになる）。複製の成功を確認するまで書き込まない
冪等性主キーで INSERT … ON CONFLICT DO UPDATE（更新されるのは target_* の行だけ）。target_import_files の sha256 が同じファイルは既定でスキップ
トランザクション読み込みは1ファイル＝1トランザクション、マージはマスタ・馬で1つ＋1年＝1トランザクション。途中で失敗した単位はロールバックされ、次回に再実行される
ログ既存の logs/keiba_YYYYMMDD.log に、ファイル単位（行数・取込数・スキップ数・所要時間）と種別単位の合計を INFO で出す。runs に1行
不正行列数違い・ID形式違い・必須値欠損・数値変換失敗は、ファイル名・行番号・理由を parse_warnings とログに残してスキップ（握りつぶさない）
重複行horse_data の重複血統登録番号は data_created_date が新しい行を採用し、捨てた行もログに残す
順序1ファイル（例: race_data_2024.csv と horse_data_2026_4sai.csv）で試す → 件数と重複期間の一致を確認 → 全ファイル
所要時間・DB増分実測：全量で約3分。DBは 171MB → 1.43GB（08）
